# Cloudflare setup (work in progress)

The Worker (`malika`) serves the Vite build and `/api/*` on the same HTTPS origin. It uses a single Cloudflare D1 database (`malika-db`) for catalogue, admins, sessions, orders and uploaded product images (stored as base64 in the `images` table, with no R2 dependency). Do not deploy as a production store until the limitations below are addressed and a staging deployment has been tested.

## Create resources

1. Install Node.js 20+ and dependencies with `npm ci`, then authenticate with `npx wrangler login`.
2. Create D1 with `npx wrangler d1 create malika-db` (no credit card is required on Cloudflare's free D1 tier). Copy its database ID into `wrangler.jsonc` in place of `REPLACE_WITH_D1_DATABASE_ID`.
3. Run `npx wrangler d1 migrations apply malika-db --remote`. For a local database use `--local` instead.
4. Run `node scripts/create-admin.mjs` in a private terminal. It prompts for username and password (the password **is visible as typed**). Use a unique password of at least 16 characters. The resulting ignored file contains a salted password hash, not the password. Run `npx wrangler d1 execute malika-db --remote --file=admin-bootstrap.local.sql`, then securely remove that file. For local development use `--local`. Never commit or share the bootstrap file. There are no Worker secrets required for the present implementation.
5. Build and deploy with `npm run build` and `npx wrangler deploy` (or in Cloudflare Workers Builds → Settings → Build: set **Production branch** to `main1`, **Build command** to `npm run build`, and **Deploy command** to `npx wrangler deploy`; `wrangler.jsonc` also defines `previews.d1_databases` so `npx wrangler preview` succeeds on non-production branches — note that it currently points to the same `malika-db` ID unless you create a separate preview D1 database). Configure a custom domain in Cloudflare if desired. HTTPS is required for the secure session cookie. For local testing: `npm run build` and `npx wrangler dev --local`. Use Wrangler rather than Vite alone to serve the API.
6. Open `/admin`, log in, and add real products. D1 starts empty intentionally; no example catalogue is inserted. Existing GitHub-published product data is not automatically imported.

## D1 image storage & free-tier limits

- Uploaded images are validated (JPEG, PNG or WebP magic bytes), capped at **1 MB (1,000,000 bytes)** raw (~1.33 MB base64), and stored in the D1 `images` table (`migrations/0008_d1_images.sql`).
- Admin uploads use `POST /api/admin/images` (also aliased at `POST /api/images` with owner session authentication) and return `{ id, url: "/api/images/<id>" }`. Public reads use `GET /api/images/<id>` with immutable `Cache-Control` headers and Worker Cache API caching where supported.
- The admin UI automatically downscales and compresses images larger than 1 MB in the browser before uploading. Compress high-resolution assets beforehand if transparency/detail must be tuned manually.
- Cloudflare D1's free plan provides 5 GB total storage and 5 million rows read / 100,000 rows written per day. Serving uncached images from D1 counts toward D1 row reads and Worker CPU limits (10 ms CPU on the free Workers plan); keep uploaded images compact (ideally 100–300 KB WebP/JPEG).

## Important limitations before production

- Bulk import merges up to 100 validated products into D1 atomically; matching IDs are updated and other products are retained. The legacy catalogue reset remains unavailable. Imported/new sizes begin with zero stock until configured in Inventory. The existing GitHub publishing workflow still applies to site content/settings, but not to the live D1 catalogue. Content/settings are not stored in D1 and still use the existing browser/GitHub workflow. Category filters are defined in the frontend rather than loaded from the categories API.
- Set rates for each governorate in the Delivery & discounts tab (exact English names listed there). No shipping rates are seeded; unconfigured governorates cannot place orders. Rates, thresholds and prices are whole EGP. Coupons are percentage discounts, rounded down, and consume one use when an order is created (cancellation does not return the coupon use). Checkout requires review of a server quote, then rechecks shipping, coupon, price and stock when placing the order. Payment integration is not implemented.
- Checkout messaging windows may be blocked by the browser after asynchronous saves. The tracking link appears on the confirmation screen; customers must save it. It is a bearer secret: anyone with the link can see the order ID, status and creation time. Old orders have no tracking link. The browser polls for new orders only while the Orders view is open; optional browser notifications require permission. Email, SMS and background push are not implemented.
- The order list supports status and order ID/phone search with pagination (date filtering is not implemented). The Images tab deletes D1 image rows only after checking product references (`images` and `cutout`) and creates a `deleted_images` tombstone in the same D1 batch transaction to block later product references. Site content/settings and external sites are not checked; the owner must verify those references before deleting. Browser caches may retain deleted images until expiry.
- Login throttling is a simple D1 per-IP counter, not a comprehensive abuse prevention system. Add Cloudflare WAF/rate limiting, monitoring, backup and a recovery procedure before launch. Sessions have an eight-hour absolute expiry and a 30-minute server-side idle expiry; the security tab supports password changes and revokes all sessions. The owner can create or delete order-only staff accounts in Security; staff can view/update orders and change their own password but cannot access owner API endpoints (including image uploads/deletions). Audit entries record product, image, order-status and password changes.
- No browser end-to-end or real Cloudflare deployment testing has been performed. Review the complete integration, security and data validation in a staging environment, including direct product links, concurrent updates, retries and D1 storage/CPU limits, before accepting real orders.

## Remaining requested features

Email/SMS notifications, background push, automatic backups and actual WAF configuration are not implemented. Cloudflare account access and a notification provider are needed for those operations. Idempotency protects retries with the same key and payload, but is not a substitute for fraud prevention; the browser keeps a pending key in session storage until the customer clears the bag. Order-item triggers recheck active product prices and stock in the same D1 batch transaction as the order and stock reservation. If the catalogue or stock changes during checkout the transaction is rolled back. Cancellation restores reserved stock once; existing pre-migration orders do not restore stock. Test backups and recovery, and deploy to a staging environment before accepting orders.

## Manual backups and Cloudflare protection (not automated)

- Apply migrations before deploying the new Worker: `npx wrangler d1 migrations apply malika-db --remote`. Existing and newly added sizes start at zero stock; set quantities in the Inventory tab.
- For a manual D1 export, run `npx wrangler d1 export malika-db --remote --output /secure/location/malika-backup.sql`. Store it encrypted and access-restricted: it contains customer details, password hashes and base64-encoded product images (so export size grows with uploaded images). Verify restoration against a separate test database, never over production. This command does not schedule backups.
- In the Cloudflare dashboard, configure WAF managed rules and rate-limiting rules available on your plan for `/api/login` and `/api/orders`; test in staging before enforcing. Rules, limits and availability depend on the zone and plan. This repository does not provision WAF rules, external notifications or scheduled backups.
- Run the isolated trigger tests with `python3 -m unittest discover -s tests -v`. SQLite tests supplement, but do not replace, Cloudflare staging and browser end-to-end tests.
